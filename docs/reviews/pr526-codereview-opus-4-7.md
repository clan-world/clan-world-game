# Phase Super-Swarm Review — PR #526 (head ba8d426)

## SUMMARY

NEEDS_FIXES. The compose topology and admin-key lifecycle (instance-secret in the volume, derived admin key on the host) are sound, and the loopback socat pattern keeps prod surface-area constrained. But the bootstrap → deploy happy path has at least three real footguns: the Makefile silently writes an empty admin-key file on subcommand failure, the bootstrap target does not start the dev loopback proxy that the documented next step depends on, and the hosted-to-self-hosted import omits `--include-file-storage` (asymmetric with backup-convex.sh). Plus a CLI/runtime version skew (1.39.1 CLI vs 1.17.4 `convex` workspace dep) that the codex 5.5 reviewer also flagged. Recommend a small fix-round to address HIGH items, then re-merge.

## HIGH severity findings

- **`Makefile:31-37` — admin-key bootstrap chained with `;`, not `&&`; silently writes an empty key on failure.** The recipe runs `docker compose exec -T convex-backend ./generate_admin_key.sh > "$$tmp" ; install -m 600 "$$tmp" ... ; sha256sum ... ; echo ...`. Make does NOT implicitly `set -e` inside a backslash-continued recipe — only the FINAL command's exit code propagates. If `generate_admin_key.sh` fails (backend transiently unready right after `up -d`, image version drops the script, exec returns non-zero), `$tmp` ends up empty or partial, `install` happily writes a 0-byte key file at 600, sha256sum hashes it, the recipe prints "Wrote ..." and exits 0. Operator then runs `make deploy-convex` and gets an opaque "unauthorized"/auth-failure with no signal that the bootstrap was the culprit. Fix: change `;` separators to `&&`, OR prepend `set -e -o pipefail;` at the top of the chained block, AND assert `[[ -s "$$tmp" ]]` before `install`.

- **`Makefile:23` — `bootstrap-convex-admin-key` only starts `convex-backend`, not the dev-port socat proxy that the documented next step requires.** `docker compose --profile dev up -d convex-backend` brings up only that service (convex-backend-dev-port has no `depends_on` reverse-edge that would pull it in). The runbook then says `make deploy-convex`, which exports `CONVEX_SELF_HOSTED_URL=http://127.0.0.1:3210` and expects the CLI to reach the backend over loopback. Without the socat proxy running, that loopback is dead. The same is true for the manual `convex env set ...` block in the runbook. Fix: have the bootstrap target also `up -d convex-backend-dev-port` when PROFILE=dev, OR add an explicit `make up-dev` (or `docker compose --profile dev up -d`) preceding step in the runbook.

- **`bin/import-convex-schema.sh:75` — hosted-export step omits `--include-file-storage` while `backup-convex.sh:44` includes it.** The script's stated purpose is replacing self-hosted data with a hosted snapshot via `--replace-all` (line 86). If any Convex table now or in the future stores file references, the import will atomically wipe self-hosted file storage. Asymmetric with the backup script and inconsistent with the `--replace-all` semantics. Fix: pass `--include-file-storage` on line 75, and add a fail-safe when `HOSTED_CONVEX_EXPORT_ZIP` is supplied externally (require an operator flag confirming the zip is file-storage-complete, since the script can't inspect zip contents).

## MEDIUM severity findings

- **`apps/server/package.json:21` vs scripts using `npx -y convex@1.39.1` — Convex CLI/runtime version skew.** The workspace dep is pinned `"convex": "1.17.4"`, but `convex:codegen` and `convex:deploy` invoke `npx -y convex@${CONVEX_CLI_PINNED_VERSION:-1.39.1}`. That is ~22 minor versions of drift between the CLI generating `_generated/` files and the runtime types that `apps/server/convex/*.ts` resolves against. Even when codegen output is "compatible," subtle internal-API contract drift (validator shape, `internalAction` vs `internalMutation` plumbing, _id codec) has historically broken builds. Fix: align workspace `convex` dep with `CONVEX_CLI_PINNED_VERSION`, OR pin both to the same minimum version that supports self-hosted (`1.18.x` was the first; 1.17.4 likely needs to bump anyway).

- **`packages/sdk/convex/schema.ts` codegen still uses workspace `convex` (1.17.4), but server uses 1.39.1.** `bin/deploy-convex.sh:46-47` runs `pnpm --filter @clan-world/sdk codegen` (which resolves to local `convex@1.17.4` per `packages/sdk/package.json:21`) and then `pnpm --filter @clan-world/server convex:codegen` (npx 1.39.1). The two packages will emit `_generated/` files from DIFFERENT CLI versions against the same SDK schema, which can produce subtly divergent type surface or version-specific helper exports. The newly-added `packages/sdk/package.json:22` `convex:codegen` script (npx 1.39.1) appears intended to fix this but is never invoked. Fix: switch the deploy script to call `pnpm --filter @clan-world/sdk convex:codegen` for consistency, OR drop the new SDK `convex:codegen` script if it really IS dead code.

- **`docker-compose.yml:97-98, 122` + `.env.template:222-228` — default origin values are dev-localhost; no prod fail-loud.** With `CHAIN_NETWORK=prod`, `CONVEX_CLOUD_ORIGIN` and `CONVEX_SITE_ORIGIN` still fall back to `http://convex-backend:3210/3211`, and `CONVEX_DASHBOARD_DEPLOYMENT_URL` defaults to `http://convex-backend:3210`. The backend will advertise these to browser clients, which obviously cannot resolve the docker-internal hostname. Fix: make these `${VAR:?...required for prod}` when `CHAIN_NETWORK=prod` is set, OR document and enforce a `.env.prod` overlay with no default fallback.

- **`docker-compose.yml:127-131` — dashboard healthcheck changed from `wget --spider` to `curl -f` without evidence the image ships curl.** The prior code used `wget` explicitly because the dashboard image (Next.js Node container) historically does not include curl. `bin/check-stack-health.sh` also assumes `curl` is present in both backend and dashboard exec contexts. If curl is absent, the dashboard's `service_healthy` never resolves; `depends_on` for `convex-dashboard-dev-port` hangs; the documented `make check-stack-health` (missing target — see LOW) reports false RED. Fix: either revert to `wget`, or `docker run --rm ghcr.io/get-convex/convex-dashboard:<tag> which curl` and confirm; commit a one-line smoke result in the runbook.

- **`Makefile:31-37` + `docker-compose.yml:107-111` — healthcheck timing is asymmetric.** The bootstrap polling loop allows 30 seconds (30 × 1s), but the compose healthcheck has `start_period: 10s` + `interval: 5s` + `retries: 3` + `timeout: 3s` ≈ ~24-28s of total grace before depends_on consumers (heartbeat, dashboard, elders) see "unhealthy" and back off. Fresh SQLite init plus image pull on a cold host can exceed this. Tightening healthcheck while loosening bootstrap is inconsistent. Fix: bump `start_period` to 30s and `retries` to 5-6.

- **`bin/backup-convex.sh:42-44` — backups directory + zip created with default umask.** `mkdir -p agents/backups` produces 0755; the zip inherits 0644. The export contains all Convex data including potentially `INDEXER_SECRET`, `WEBHOOK_SHARED_SECRET`, and user-table contents. Fix: `install -d -m 0700 agents/backups` and `chmod 0600 "$backup_path"` after the export completes. Mirror the .gitignore + .dockerignore exclusions that the PR correctly adds.

- **`bin/{deploy,backup,import-convex-schema}.sh:check_cli_version` — tautological check.** All three scripts compute "actual = `npx -y convex@${CONVEX_CLI_PINNED_VERSION} --version`" and compare against `expected = ${CONVEX_CLI_PINNED_VERSION}`. Since `npx -y convex@X` always materializes exactly version X, the two strings always match. The check provides no protection against drift, registry compromise, or operator override. Fix: drop the check, OR invoke `npx --no-install convex --version` (or `npm view convex@${CLI_PIN} version`) to actually verify the resolved binary's version.

- **Runbook documents `convex env set <var>` (lines 48-54) without using the pinned CLI.** Bare `convex env set` resolves to whatever's first on PATH — possibly a different version than `CONVEX_CLI_PINNED_VERSION`. The whole point of the pin is to prevent the operator from accidentally hitting hosted Convex or producing version-skewed env state. Fix: prefix with `npx -y convex@${CONVEX_CLI_PINNED_VERSION:-1.39.1}` in the runbook block, AND add a `make convex-env-set` wrapper (or `make bootstrap-convex-indexer-env`) that reads from .env + secrets files and bulk-applies, so missing one of the seven required calls (silent flag-off path) isn't possible.

## LOW severity findings

- **`Makefile` — no `check-stack-health` target.** `bin/check-stack-health.sh` exists but is only invokable by raw path. Inconsistent with `deploy-convex`/`backup-convex`/`import-convex-schema` having make targets. Add it.

- **`bin/import-convex-schema.sh:64-67` — `SDK_SCHEMA_SHA256` check is opt-in.** Without setting the env var, the schema fingerprint check is skipped. The intent (catch drift between SDK schema and the export's expected schema) is good, but a missing-by-default safety net is no safety net. At minimum, emit "WARN: SDK_SCHEMA_SHA256 not set — skipping schema-drift check" when unset.

- **`Makefile:45 reset-anvil` — `docker volume rm clan-world_anvil_data || true` masks real failures.** If the volume is held (anvil-fork didn't stop), the `|| true` swallows the error and the next `up -d` runs against the same old state. Drop the `|| true` (the preceding `stop` + `rm -f` should have freed it).

- **`docker-compose.yml:139-140, 151-152` — socat 1.7.4.4 has no per-host connection cap.** Loopback-only and dev-only, so practical impact ≈ 0, but `socat … fork,reuseaddr` will happily spawn unbounded child procs. Consider `max-children=8` or similar.

- **`docker-compose.yml:93, 117` — `stop_grace_period: 10s`.** Tight for SQLite flush + WAL checkpoint on heavy state. 30s is the conventional value for stateful services.

- **`docs/runbooks/self-hosted-convex.md` — no `docker compose pull` step.** First-bootstrap on a fresh host with `CONVEX_BACKEND_TAG=latest` will materialize whatever `latest` happens to be at that minute. For determinism, runbook should call out `docker compose pull` and (better) pinning by SHA, as `.env.template:212-213` already notes.

- **`Makefile:23` — `convex-backend` service name hardcoded in recipe twice.** If service name ever changes, both `up -d` and the `exec` loop must be updated in lockstep. Define `CONVEX_BACKEND_SERVICE ?= convex-backend` at the top.

- **`packages/sdk/package.json:22` — `convex:codegen` script appears dead.** Not called by the deploy script, not referenced by the runbook. Either wire it in (preferred, see MEDIUM item) or remove it to avoid drift between SDK and server packages.

- **`bin/check-stack-health.sh:52` — `check_exec` against `convex-backend:3211/` only available via `check_exec_any_status`.** The accept-any-status helper is correct because `/` on the actions site may return 404 normally, but the success vs. failure semantics could mislead operators. Print "(expect 200/404)" alongside the URL.

- **`bin/import-convex-schema.sh:74-76` — `unset CONVEX_SELF_HOSTED_URL CONVEX_SELF_HOSTED_ADMIN_KEY` happens inside the export-only branch.** If `HOSTED_CONVEX_EXPORT_ZIP` was supplied (skipping export) and an operator's shell still has `CONVEX_SELF_HOSTED_*` set, downstream `convex_cli` calls will see them. The `export_self_hosted_env` call later does set them, so net behavior is correct, but the asymmetry is a footgun on script edits.

## Cross-cutting observations

- The instance-secret-in-volume + derived-admin-key design (over the prior file-mounted-secret design) is the right call: the key file becomes an operator credential that can be regenerated from the persisted root, and it stays out of `docker inspect` and image layers. The `convex_data` volume warning is loud and correct.
- The PR consistently uses 127.0.0.1 binding for the dev socat proxies — good. Prod keeps Convex Docker-internal — good. The remaining prod-readiness gap is the localhost-origin defaults (MED above).
- The `CONVEX_WEBHOOK_URL=http://convex-backend:3211` plumbing is correct for the heartbeat container's HTTP-actions path; sibling PR #525 consumes it (not flagged per the brief).
- Codegen/CLI version discipline is the dominant pre-merge risk after the bootstrap bugs above. Once the workspace `convex` dep matches the pinned CLI, much of the surrounding tautology disappears.
