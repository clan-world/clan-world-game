# Phase Super-Swarm Review — PR #532 (head 1ed8d60)

## SUMMARY
NEEDS_FIXES. The Docker/Convex scaffolding is broadly coherent, and the SettleLatch references are removed cleanly, but the integrated phase leaves the full runner and the new heartbeat container with no coordination boundary and no prod image-pin enforcement. I would not merge until the heartbeat ownership/settle-window invariant is made explicit in code and prod refuses mutable image tags.

## HIGH severity findings
- `packages/runner/src/main.ts:137`, `packages/runner/src/heartbeatScheduler.ts:121`, `packages/runner/src/tickLoop.ts:162`: Removing `settleLatch` makes the full runner fire heartbeats independently of the Cycle B settle window. The default runner loop still starts both `startHeartbeatScheduler()` and `tickLoop()`, while `tickLoop` can spend ~90s delivering/settling a tick and the heartbeat scheduler fires from `nextHeartbeatAtTs` (60s in the target KeeperHub profile). That means the chain can advance to tick N+1 before Elders finish submitting orders for tick N, and `tickLoop` can later mark only the stale observed tick processed. Suggested fix: choose one heartbeat owner. For the full runner, either restore a coordination barrier that blocks heartbeat until Cycle B has settled the prior tick, or remove/disable the embedded heartbeat scheduler when the containerized heartbeat service is the owner. Add an integration test where `settleWindowSec > heartbeatIntervalSeconds` and assert no heartbeat fires before settle completes, or assert the full runner never starts Cycle A in containerized mode.
- `docker-compose.yml:98`, `docker-compose.yml:117`, `.env.template:212`: Prod can still run `ghcr.io/get-convex/convex-backend:latest` and `ghcr.io/get-convex/convex-dashboard:latest` because the template defaults are mutable and compose has no prod guard rejecting `latest`. For a pre-merge phase whose goal is containerized services, this is a real operational/supply-chain footgun: a prod restart can silently pull a different backend/dashboard than the one tested. Suggested fix: make prod fail-loud unless `CONVEX_BACKEND_TAG` and `CONVEX_DASHBOARD_TAG` are immutable digests or approved SHA tags, or split dev/prod defaults so only dev gets `latest`.

## MEDIUM severity findings
- `docker-compose.yml:169`, `packages/runner/src/main.ts:137`, `packages/runner/README.md:61`: The new heartbeat service does not prevent the existing full runner from also running Cycle A. If an operator keeps the old `pnpm --filter @clan-world/runner start`/systemd path alive while bringing up compose heartbeat, both processes can call `heartbeat()` with different `RUNNER_ID`s and wallets. On-chain rate limiting reduces damage but creates noisy reverts, misleading runnerStatus rows, and alert churn. Suggested fix: add a single explicit mode/env gate such as `RUNNER_HEARTBEAT_ENABLED`, default it off for the full runner when compose heartbeat is used, and document the mutually exclusive launch paths.
- `Makefile:20`, `docker-compose.yml:56`: `make bootstrap-convex-admin-key` starts `convex-backend` before the admin-key Docker secret file exists, but the current compose service still declares that secret. On a clean checkout this makes the bootstrap target fail at compose creation time instead of generating the key. The inline diff appears to remove the backend admin-key secret, but the checked-out file still has it; ensure the submitted head really has the removal.
- `.env.template:221`, `.env.template:224`, `.env.template:230`: The dev Convex origins mix `127.0.0.1` and `localhost` despite the comments in the inline diff calling out exact-origin consistency. Convex/browser/dashboard origin checks are exact-string sensitive. Suggested fix: standardize all dev defaults to one host spelling.

## LOW severity findings
- `agents/heartbeat/entrypoint.sh:41`: The worktree version reads `WEBHOOK_SHARED_SECRET_FILE` without trimming trailing whitespace or rejecting embedded newlines/CR, while the inline diff contains stronger validation. If the final head has the stronger version, this is clean.
- `bin/check-stack-health.sh:39`: The inline diff improves `check_exec_any_status` to classify 5xx as RED, but the worktree version only checks curl exit status and can report HTTP 500 as GREEN. Confirm the submitted head contains the HTTP-code parsing version.

## Cross-cutting observations
SettleLatch removal is syntactically complete in the inline diff: imports, interfaces, tests, and deleted files are cleaned up. The replacement pattern is not yet safe for the full runner path because the phase moved from one coordinated state machine to two independent heartbeat/tick loops without a hard ownership gate.

The self-hosted Convex flow is close: host loopback proxies, backup/import scripts, destructive-import confirmation, and `/convex/data` persistence are the right shape. The remaining risk is mostly operational: prod immutability and exact launch/config invariants need code-level enforcement, not comments.
