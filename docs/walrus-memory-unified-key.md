# Walrus Memory — unified-key mode (bonus)

**BLUF:** `scripts/walrus/provision-elders.mjs` now has an optional `--owner-source=base-key`
mode where each Elder's Sui **memory-account owner** is derived from its **existing
secp256k1 Base/EVM private key** — one cryptographic identity spanning the ClanWorld
EVM game *and* the Walrus encrypted-memory layer. The default stays `ed25519` (fresh
Sui key per Elder), so the 4 already-provisioned live mainnet accounts are untouched.

The demo line: *"Elder N's Base wallet `0x71C4…` also OWNS its Sui encrypted-memory
account `0xd64b…` — same key, two chains."*

---

## The one-identity story

Elders already hold a secp256k1 Base/EVM key (their on-chain clansman wallet, in
`~/.secrets/clanworld-elder-wallets.json`). Sui supports secp256k1 accounts natively,
so the *same* 32-byte secret can own a Sui object — including a Walrus Memory account.
Unified-key mode makes the Elder's Base wallet the owner of its memory account instead
of minting a throwaway Ed25519 Sui key. Provenance becomes self-evident: anyone can
verify the Base wallet and the memory-account owner are the same key.

## The footgun: `walletSigner`, NOT `suiPrivateKey`

MemWal's `createAccount({ suiPrivateKey })` / `addDelegateKey({ suiPrivateKey })`
helpers **always** do `Ed25519Keypair.fromSecretKey()` internally. If you hand them a
secp256k1 Base key as `suiPrivateKey`, they will **silently derive a different
(Ed25519) owner** — the account is created under the wrong address and the "same key
on both chains" claim is false.

For a secp256k1 owner you **must** use the `walletSigner` adapter path instead:

```js
const keypair = Secp256k1Keypair.fromSecretKey(hexToBytes(baseKey)); // 32 raw bytes
const walletSigner = {
  address: keypair.getPublicKey().toSuiAddress(),
  // memwal calls this as signAndExecuteTransaction({ transaction }) and reads .digest
  async signAndExecuteTransaction({ transaction }) {
    const r = await rpc.signAndExecuteTransaction({
      signer: keypair, transaction,
      options: { showEffects: true, showObjectChanges: true },
    });
    return { digest: r.digest };
  },
  async signPersonalMessage(message) { return keypair.signPersonalMessage(message); },
};
await createAccount({ packageId, registryId, walletSigner, suiClient, suiNetwork: "mainnet" });
```

Two more gotchas, both handled in the script:

- **`Secp256k1Keypair.fromSecretKey` rejects plain/`0x` hex.** It accepts a raw
  `Uint8Array(32)` or a Bech32 `suiprivkey1…`. The Base key in the wallets file is
  `0x`-prefixed hex → convert with `hexToBytes()` first.
- **`suiPrivateKey` and `walletSigner` are mutually exclusive** — memwal throws if
  both are set. The script picks exactly one via `ownerSignerOpts(owner)`.

**Delegate keys stay Ed25519.** Only the *owner* is the Base key; the runtime
credential (the delegate that the MCP uses to `remember`/`recall`) is still a fresh
Ed25519 key generated by `generateDelegateKey()` and registered via the walletSigner.

## Blast-radius tradeoff (acceptable for game v2)

Reusing one key across Base and Sui means a leak of an Elder's Base key compromises
**both** its clansman wallet and its Sui memory account. This is acceptable for the
ClanWorld game v2 because the Base keys only authorize **clansman game actions** (no
treasury / no human funds), the memory contents are non-sensitive game continuity
notes, and the Elders are sandboxed agents. For any future identity that guards real
value, keep the keys separate (the default `ed25519` mode). The owner key is only
needed at provisioning/rotation time; the runtime container only ever sees the
Ed25519 delegate, never the Base key.

## How to run base-key provisioning

Creds land in a **separate** dir (`~/.secrets/clanworld-elder-walrus-unified/elder-N/`)
so they can never clobber the working fresh-key creds in `clanworld-elder-walrus/`.

```bash
# 1. Free offline proof — derive all 4 Base→Sui owners, no network, no spend:
NODE_PATH=<deps> node scripts/walrus/provision-elders.mjs --owner-source=base-key --derive-only

# 2. Full base-key provisioning (mainnet — funds each Base-derived owner, creates
#    its memory account + Ed25519 delegate via the walletSigner path):
NODE_PATH=<deps> node scripts/walrus/provision-elders.mjs --owner-source=base-key
# (or:  WALRUS_OWNER_SOURCE=base-key node scripts/walrus/provision-elders.mjs)
```

Env knobs:

- `WALRUS_OWNER_SOURCE=ed25519|base-key` — same as `--owner-source`.
- `WALRUS_DERIVE_ONLY=1` — same as `--derive-only`.
- `WALRUS_ELDER_WALLETS_PATH` — override the Base wallets file location.

The full run reuses the existing idempotency / per-run funding cap / isolation-proof
machinery; only the owner-key source and the creds dir change. Funding a
Base-derived owner is the *only* extra step versus default mode — the signing path
is otherwise identical.

A live one-Elder account-create was deliberately **not** run: the cryptographic path
is fully proven, and creating a permanent on-chain account under an Elder's Base
identity is irreversible — best done intentionally (with funding) when switching the
live Elders to unified-key mode, not as a throwaway proof. The only gap to a live
create is funding the Base-derived owner; the signing is proven.
